# Step 5 — Final summary comment

this document owns final-summary routing and rendering. `SKILL.md` links here for the terminal-status exceptions, templates, and comment identity rules.

## Terminal-status routing

| Status | PR comment template |
| --- | --- |
| `SUCCESS` | Ready-to-merge template |
| `MAX_ITERATIONS`, `NO_PROGRESS`, `TESTS_REGRESSED`, `CI_STUCK`, `EXTERNAL_PUSH` | Needs-attention template |
| `SCOPE_SPLIT_RECOMMENDED` | Needs-attention template with the **Recommended split** section populated from the `pr_scope` block in state |
| `REVIEW_INCOMPLETE` | a required review or comment operation did not complete. report the failed operation locally; do not post a final pr comment. |
| `SETUP_ERROR` | **No PR comment.** Print stderr message and return (see exception below). |
| `DRY_RUN_COMPLETE` | **No PR comment.** Report the synthesized partitions to the user and return. A dry run inspects the PR; it does not write to it. |

## Terminal metric write (mandatory)

On comment-posting statuses, run this after the summary comment is posted or updated, never before: the script marks the loop completed, and a marker written ahead of a failed post would make the next run reinitialize instead of delivering the summary. on `SETUP_ERROR`, `REVIEW_INCOMPLETE`, and `DRY_RUN_COMPLETE`, run it before returning:

```bash
TERMINAL_STATUS=<status> bash "$SKILL_ROOT/scripts/write_terminal_metric.sh"
```

The script reads `<git-dir>/pr-loop/state.json`, emits the terminal rollup (knobs + totals + wall-clock seconds since `loop_started_at`), and, before the append, marks the state file with the lowercase `status` and a `completed_at` timestamp so the next invocation on the same PR reinitializes instead of resuming. Runs once per loop on every terminal status, including `SETUP_ERROR`, `REVIEW_INCOMPLETE`, and `DRY_RUN_COMPLETE`. If it fails, log to stderr and continue — the comment (when posted) is the user-visible deliverable and must not be blocked on metric persistence; on `SETUP_ERROR` and `REVIEW_INCOMPLETE` the stderr return path also continues regardless.

## Local terminal output (not the posted comment)

Separate from the posted PR comment, the Step 5 terminal (stdout) output may include a per-iteration model-routing recap read from `history[].model_routing` — e.g. `iter 2: reviewer=sonnet, adversary=opus, delta_gate=haiku`. This is local observability for the operator and is governed by [`model-overrides.md`](model-overrides.md#observability-and-recording). It must **never** be written into the posted PR comment: concrete model/tool names there violate the attribution rule below.

## Comment identity + attribution rules

Post or update a single PR comment, identified by the HTML marker `<!-- pr-review-loop-summary -->` on its first line. The marker is invisible to readers and used to find-and-update the same comment across iterations — never post multiple summary comments.

**The visible body must not claim attribution.** No tool name, no "this was generated by", no "automated review" branding, no signatures. Write it as a neutral review summary stating what was checked, what was found, and what was addressed. Do not mention the skill name, "PR Review Loop", the reviewer persona names as tool identifiers, or internal status codes (`SUCCESS`, `MAX_ITERATIONS`, etc.).

## Exception — `DRY_RUN_COMPLETE`

Do **not** post or update a PR comment when the terminal status is `DRY_RUN_COMPLETE`. `dry_run=true` runs the panel and synthesizes, then exits from §4c without applying, committing, or pushing. Report the synthesized `{blockers, suggestions, nits}` partitions to the user in the session instead. §4c invokes §4i on its no-commit path first, so the findings still reach `history[]` and the terminal metric; the comment disposition/reply step is skipped along with the summary comment.

## Exception — `SETUP_ERROR`

Do **not** post or update a PR comment when the terminal status is `SETUP_ERROR`. The terminal metric write (above) still runs with `TERMINAL_STATUS=SETUP_ERROR` so the metric record exists; only the PR comment is skipped. After the metric write, print a concise stderr message identifying the script and exit code (e.g. `SETUP_ERROR: scripts/fetch_sonar.sh exited 1 — jq not installed`) and return without touching the PR. This status indicates a local tooling problem; there is nothing for the PR author to act on.

## Promoted-item provenance suffix

For any `addressed` or outstanding item whose history record carries `promoted_from: "suggestion"`, key the suffix on `promotion_reason` (the schema's canonical field on `addressed[]`/`deferred[]` provenance objects), not on `promoted_by` alone — three of the schema's `promotion_reason` values carry `promoted_by: "adversary"` and they describe different paths:

- `Promoted from suggestion (agreed by <N> personas)` when `promotion_reason: "multi_source"` (N = `source_reviewers.length`).
- `Promoted from suggestion (endorsed by adversary)` when `promotion_reason: "adversary_endorsed"` — the adversary endorsed an existing panel suggestion via the [§4d.0.5 matcher](synthesis.md#matcher).
- `Promoted from suggestion (adversary finding with verified evidence)` when `promotion_reason: "evidence_gated_solo_adversary"` — the adversary raised the suggestion alone and the [§4d.0.5 evidence gate](adversary.md#evidence-gate-verification-evidence-gated-solo-adversary-path) promoted it; no panel suggestion was endorsed.
- For `promotion_reason: "evidence_verification_failed"` the item lives on `deferred[]` (not promoted), so no suffix renders; the deferred bullet uses the standard `<file:line> — <summary>` shape from `templates/summary_needs_attention.md`.

The canonical home for the `promotion_reason` enum is `templates/state.schema.json`; if values are added or removed there, update the bullet list above to match.

The suffix follows the file:line — summary text on the same bullet, separated by " — ".

## Carrying open suggestions and nits

Both templates render their suggestion and nit bullets from the **open sets** — every such finding the loop raised and nothing has settled since — not from one iteration's partitions:

```bash
echo '{"iteration": <n>, "suggestions": [...], "nits": [...], "blockers": [...], "findings": [...], "deferred": [...],
       "panel_ran": [...], "reviewer_errors": [...], "shallow_review": [...],
       "forced_full_sweep": <bool>}' \
  | python3 "$SKILL_ROOT/scripts/collect_open_findings.py" --state "$(git rev-parse --git-dir)/pr-loop/state.json"
```

stdin is this iteration's synthesized partitions, passed through from `promote_findings.py` unchanged, plus the raw findings used to build this iteration's history and what §4a.1 and §4c know about who reviewed. Retain out-of-scope findings for this input before rendering their deferral strings. The script walks `history[]` and returns `{suggestions, nits, carried}`.

| Field | What to pass |
| --- | --- |
| `iteration` | The iteration Step 5 is exiting from, read off `history[]` rather than computed: `history[-1].iteration` when §4i already appended this iteration (the §4d.1 `SUCCESS` path, and any other path where you ran §4i), `history[-1].iteration + 1` when it did not, and `0` when `history[]` is empty. Do not derive it from `state.iteration` — that is the *last appended* entry's number, which is the same value in the first case and one short in the second. |
| `suggestions`, `nits` | This iteration's partitions verbatim. Do not add a `reviewer` field — the owner is read from `source_reviewers`, which is what a synthesized finding carries. |
| `blockers` | De-duplication only. A promoted suggestion belongs under **Outstanding blockers**, not in both sections. |
| `findings`, `deferred` | Raw current findings, including out-of-scope items, and the current deferral partition. These settle prior open items even before history is appended. Deferral strings remain presentation text; structured provenance retains the identity of failed-evidence findings. |
| `panel_ran` | `panel_selection.ran` for this iteration. |
| `reviewer_errors`, `shallow_review` | This iteration's, from §4c. Selection is not review: without these, a persona whose output failed validation or came back shallow reads as having looked again. |
| `adversary`, `adversary_shallow_giveup` | Optional, and shaped like their `history[]` counterparts. Pass them when §4d.0 ran this iteration; the adversary is not in `panel_ran`, so without them it reads as not having reviewed. |
| `forced_full_sweep` | `true` when the pre-approval sweep ran the full panel. |

Run it on every terminal status that posts a comment; an empty set omits its section like any other. `iteration: 0` is legal and is what an empty `history[]` calls for — `SCOPE_SPLIT_RECOMMENDED` from Step 3.5, and `EXTERNAL_PUSH` from §3.6 on a first run — and it returns empty sets because there is nothing to accumulate. A §3.6 abort on a *resume* is not that case: `history[]` is populated, so pass the real number and the accumulated sets come back. `DRY_RUN_COMPLETE` posts no comment and reports its own partitions from §4c.

Why it exists: a delta-gated iteration runs a subset of the panel (`docs/delta-gate.md`), so a suggestion or nit raised earlier is persisted in `history[].findings` and counted in `n_suggestions` / `n_nits`, then never revisited. Rendering only the last iteration's partitions drops it. The pre-approval forced full sweep closes that gap on the approval path alone; `MAX_ITERATIONS`, `NO_PROGRESS`, `TESTS_REGRESSED` and `EXTERNAL_PUSH` all exit without one.

### Resolution rule

An item raised in iteration `i` stays open unless some later iteration settled it:

| What a later iteration did | Effect on the item |
| --- | --- |
| Re-raised it (matched per [the §4c rule](synthesis.md#matcher)) | Stays open with the newer file/line, still dated `first_seen_iteration: i` |
| Re-raised it as a blocker, promoted it, or deferred it | Dropped — that section owns it now |
| Ran its owning persona and did not re-raise it | Dropped — the owner looked again and let it go |
| Skipped its owning persona | Settles nothing; the item carries |

An item's owning personas are its `source_reviewers` — every one of them, since §4c unions that list when two personas surface the same issue and one going quiet is not the panel withdrawing it. "Ran" reads `panel_selection.ran`, widened to the whole panel by `forced_full_sweep` or `mode: "full"`, minus anyone in `reviewer_errors[]` or `shallow_review[]`.

Owners **accumulate across sightings**; a re-raise never narrows them. `source_reviewers` is a per-iteration artifact — [`docs/synthesis.md`](synthesis.md) notes that `promote_findings.py` counts it within one call and never reads `history[]` — so a delta-gated iteration that runs one of two co-owners re-raises the finding with the shorter list, and reading the newest sighting's list would let that persona alone retire what the panel co-owns. The item keeps the union of every list it has been seen under. Two consequences worth knowing: a finding the §4d.0.5 merge gave `adversary` as a co-owner needs an adversary re-run to be settled, which a full panel sweep is not; and `source_reviewers` must survive §4i, which is why [`templates/state.schema.json`](../templates/state.schema.json) declares it on `history[].findings[]`. A finding persisted with only the singular `reviewer` is treated as that persona's alone. The adversary is not a panel persona, so a full sweep never speaks for it — only an adversary run that dropped the finding does. A missing or malformed `panel_selection` settles nothing: a stale bullet is noise the author can wave off, while a dropped one is the defect this closes.

The §4d.1 approval entry records `findings: []` for the approving iteration, which read literally is "the full panel re-raised nothing" and would erase every carried item. Passing that iteration's own number on stdin is what folds the real partitions onto it.

### What this does not accumulate

`deferred[]` is still rendered from the last iteration's partition. An item a later iteration re-raised as `out_of_scope` therefore leaves the open sets — its owner did look again and re-tiered it — and appears under **Deferred** only if that happened in the final iteration. Out-of-scope findings are the deferral section's to accumulate, and #116 scoped the fix to the two partitions that had no venue at all; carrying deferrals is the same shape of work on a third partition.

### Rendering the open sets

Bullets keep the `<file:line> — <summary>` shape. The script drops `reviewer` from every item deliberately: the posted body must not claim attribution, and a field the renderer never receives cannot leak into it. `first_seen_iteration` and `carried` are local observability — order by them if it helps, but neither is rendered.

## Template — ready to merge (internal status `SUCCESS`)

Body lives in `templates/summary_ready.md`. Render verbatim, substituting `<N>`, the per-iteration `<...>` bullets, and the suggestion and nit bullets from the open sets above.

Pick the CI sentence from this iteration's `ci_status`: `"success"` renders `CI is green.`; `"skipped"` renders `No CI checks were found on this PR.` `SUCCESS` is reachable with `ci_status: "skipped"` when `ci_wait.sh` exits 4 (no checks ever registered), so claiming green there would assert a check that never ran.

One more case renders the same neutral sentence: `ci_wait.sh` also exits 0 when every registered check concluded as `skip` (its exit-0 contract is "all checks passed **or only skipped**"), which records `ci_status: "success"`. Before rendering green, read the buckets it wrote to `<git-dir>/pr-loop/last_ci_status.json`; if none is `pass`, nothing actually ran and the neutral sentence is the honest one.

> Example of a promoted-item bullet:
> `- src/auth.ts:42 — missing audit log on login — Promoted from suggestion (agreed by 2 personas)`

## Template — not merge-ready (any non-SUCCESS status that posts a comment: `MAX_ITERATIONS`, `NO_PROGRESS`, `TESTS_REGRESSED`, `CI_STUCK`, `EXTERNAL_PUSH`, `SCOPE_SPLIT_RECOMMENDED` — which replaces the finding sections wholesale, see below)

Body lives in `templates/summary_needs_attention.md`. Render verbatim, substituting the lead sentence, blocker bullets, CI status, iteration count, deferred bullets, and the suggestion and nit bullets from the open sets above.

> Example of a promoted-item bullet:
> `- src/auth.ts:42 — missing audit log on login — Promoted from suggestion (agreed by 2 personas)`

## Additional section — `SCOPE_SPLIT_RECOMMENDED` only

When the terminal status is `SCOPE_SPLIT_RECOMMENDED`, the needs-attention body's lead sentence is "This PR exceeds the configured size threshold (\<new_loc_total\> new LOC vs. threshold \<threshold\>) and was paused so the changes can be moved into smaller PRs." Replace the `Outstanding blockers` / `CI status` / `Iterations completed` / `Suggestions` / `Deferred` / `Nits` sections with the body in `templates/summary_split_addendum.md` — the whole run of finding sections, since no review has run yet.

If the agent returned `verdict: "atomic"` the loop never reaches this status (it continues to Step 4 instead), so this section never renders for atomic verdicts.

## Rules

- Lead with the HTML marker on line 1.
- Headings and prose are neutral — no "this loop did X", no "the agent concluded Y".
- Omit empty sections entirely (no "Deferred: none").
- Keep under ~60 lines. Link to the PR diff or file lines for anything that needs depth.
- Do not list reviewer persona names as sources. Aggregate findings by file/line, not by reviewer.
- Never name subagent models/tiers in the posted comment; model routing is local-only (see the local terminal output section above).
- a **Reviewer comments** section renders each root's latest successful disposition from `comment_ledger`, plus a brief acknowledgement of issue/review-level comments from the reviewed `human_comments` snapshot. omit the section when there were no reviewer comments. reply, ledger, and baseline mechanics: [`comment-handling.md`](comment-handling.md).
- **Do not auto-merge.** Merge is always a human action.
